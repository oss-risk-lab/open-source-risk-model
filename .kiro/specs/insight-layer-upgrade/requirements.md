# Requirements Document

## Introduction

The Insight Layer Upgrade transforms the multi-repo Overview page from a passive data display into an interpretation layer that explains system risk clearly. Currently, the Overview page shows risk labels (LOW/MEDIUM/HIGH) and lists repos/dependencies without explaining WHY the risk level was assigned, shows empty "No priority risks" dead zones when risk is low, and renders Top Risk Drivers as a plain repo list instead of meaningful signals. This upgrade adds explanation text, contextual empty states, signal-based risk drivers, and a `compute_insight_statements()` function that generates human-readable insight statements. All changes are pure interpretation and UX — no scoring formulas, graph structure logic, APIs, persistence, or layout changes.

## Glossary

- **Overview_Page**: The `ui/overview.html` page that displays the unified system risk summary for an Analysis Scope.
- **System_Risk_Summary**: The dict returned by `compute_system_risk_summary()` in `api/app.py` containing repo-level and dependency-level risk metrics.
- **Risk_Explanation**: A human-readable text string explaining WHY the aggregate risk level was assigned, following the pattern: [Conclusion] + [because] + [Reason]. Example: "Your system shows low risk because no vulnerable dependencies or high-risk repositories were detected." The explanation MUST reference at least one factor from: dependencies, repos, or maintenance.
- **Key_Factors**: A list of short strings identifying the primary factors that determined the aggregate risk level (e.g., "no vulnerable dependencies", "all repos show low maintenance risk").
- **Recommended_Action**: A short actionable string advising the user on what to do next based on the aggregate risk level.
- **Insight_Statement**: A human-readable sentence generated by `compute_insight_statements()` that provides an interpretive conclusion about the overall system risk posture (e.g., "Your system appears stable and well-maintained"). Insight Statements answer "what this means overall" and are distinct from Risk Drivers.
- **Risk_Driver_Signal**: An explanation-based entry in the Top Risk Drivers section that describes a factual signal about a specific risk factor (e.g., "No vulnerable dependencies detected"). Risk Drivers answer "what is affecting risk" and are distinct from Insight Statements.
- **Priority_Risk_Empty_State**: A contextual message displayed in the Priority Risks section when no priority risk items are computed, varying based on the aggregate risk level.
- **Dependency_Count**: The total number of unique dependencies reported in the KPI section, which must include all user-provided dependency names regardless of whether they map to a GitHub repository.
- **Compute_Functions**: The set of backend functions in `api/app.py` that produce data for the Overview page: `compute_system_risk_summary()`, `compute_priority_risks()`, `compute_top_risky_dependencies()`, `get_top_risk_drivers()`.
- **Render_Functions**: The set of frontend functions in `ui/overview.html` that display Overview page sections: `renderRiskSummary()`, `renderKPIs()`, `renderPriorityRisks()`, `renderRiskDrivers()`, `renderRiskyDeps()`.

## Requirements

### Requirement 1: Complete Dependency Counting

**User Story:** As a user, I want all dependencies I provide to appear in the Unique Dependencies count, Risky Dependencies list, and graph output, so that I have an accurate picture of my system's dependency surface.

#### Acceptance Criteria

1. WHEN a user provides dependency names in the scope input, THE System_Risk_Summary SHALL include every user-provided dependency in the `total_unique_dependencies` count, regardless of whether the dependency maps to a GitHub repository.
2. WHEN a dependency does not map to a GitHub repository, THE System_Risk_Summary SHALL still count the dependency as a unique dependency in `total_unique_dependencies`.
3. WHEN a dependency does not map to a GitHub repository, THE `compute_top_risky_dependencies()` function SHALL include the dependency in its output with `risk_score` of 0, `risk_label` of "LOW", `cve_count` of 0, and an empty `used_by_repos` list.
4. WHEN a dependency does not map to a GitHub repository, THE merged graph SHALL contain a package node for the dependency with `type` set to "package" and an empty `source_repos` list.

### Requirement 2: System Risk Explanation

**User Story:** As a user, I want the system risk summary to explain WHY my risk level is low, medium, or high and tell me what to do next, so that I understand the reasoning behind the assessment and can take appropriate action.

#### Acceptance Criteria

1. WHEN `compute_system_risk_summary()` computes the aggregate risk, THE function SHALL generate a `risk_explanation` string that follows the pattern: [Conclusion] + [because] + [Reason] (e.g., "Your system shows low risk because no vulnerable dependencies or high-risk repositories were detected.").
2. THE `risk_explanation` SHALL reference at least 1 factor from: dependencies, repos, or maintenance. IF the explanation does not reference at least 1 of these factors, THE function SHALL treat the explanation as incomplete and add a reference to the most relevant factor.
3. WHEN the aggregate risk label is "LOW", THE `risk_explanation` SHALL reference the absence of high-risk factors (e.g., no vulnerable dependencies, no high-risk repos, healthy maintenance scores).
4. WHEN the aggregate risk label is "MEDIUM" or "HIGH", THE `risk_explanation` SHALL reference the specific risk factors present (e.g., count of vulnerable dependencies, count of high-risk repos, elevated maintenance risk scores).
5. WHEN `compute_system_risk_summary()` computes the aggregate risk, THE function SHALL generate a `key_factors` list containing short descriptive strings for each primary factor that influenced the risk level.
6. THE `key_factors` list SHALL contain between 1 and 5 entries.
7. WHEN `compute_system_risk_summary()` computes the aggregate risk, THE function SHALL generate a `recommended_action` string advising the user on next steps.
8. WHEN the aggregate risk label is "LOW", THE `recommended_action` SHALL be "No immediate action required."
9. WHEN the aggregate risk label is "MEDIUM", THE `recommended_action` SHALL be "Monitor dependencies and maintenance activity."
10. WHEN the aggregate risk label is "HIGH", THE `recommended_action` SHALL be "Review vulnerable dependencies and high-risk repositories immediately."

### Requirement 3: Priority Risks Contextual Empty State

**User Story:** As a user, I want to see a meaningful message instead of "No priority risks identified" when the Priority Risks section is empty, so that I understand the context of my risk posture.

#### Acceptance Criteria

1. WHEN `compute_priority_risks()` returns an empty list and the aggregate risk label is "LOW", THE Overview_Page SHALL display a contextual message indicating that no priority risks were found because the system shows low risk across all analyzed components.
2. WHEN `compute_priority_risks()` returns an empty list and the aggregate risk label is "MEDIUM", THE Overview_Page SHALL display a contextual message indicating that while no critical risks were identified, the system shows moderate risk that warrants monitoring.
3. WHEN `compute_priority_risks()` returns an empty list and the aggregate risk label is "HIGH", THE Overview_Page SHALL display a contextual message indicating that risk data is being evaluated and recommending review of individual repo insights.
4. WHEN any per-repo result has a risk label of "MEDIUM" or "HIGH", THE `compute_priority_risks()` function SHALL return at least 1 priority risk item.

### Requirement 4: Signal-Based Top Risk Drivers

**User Story:** As a user, I want the Top Risk Drivers section to show factual, explanation-based signals about what is affecting my system's risk, so that I get actionable risk drivers distinct from interpretive insight statements.

#### Acceptance Criteria

1. THE `get_top_risk_drivers()` function SHALL return a list of Risk_Driver_Signal objects, where each object contains a `signal` string (factual statement about a specific risk factor), a `category` string (e.g., "vulnerability", "maintenance", "dependency"), and a `severity` string ("low", "medium", "high", "info"). Risk Drivers describe "what is affecting risk" (e.g., "No vulnerable dependencies detected") and are distinct from Insight Statements which describe "what this means overall" (e.g., "Your system appears stable and well-maintained").
2. WHEN no vulnerable dependencies exist in the merged graph, THE `get_top_risk_drivers()` function SHALL include a signal stating that no vulnerable dependencies were detected, with category "vulnerability" and severity "info".
3. WHEN all repositories show low maintenance risk, THE `get_top_risk_drivers()` function SHALL include a signal stating that all repositories show low maintenance risk, with category "maintenance" and severity "info".
4. WHEN one or more repositories show high maintenance risk, THE `get_top_risk_drivers()` function SHALL include a signal identifying the count of high-risk repositories, with category "maintenance" and severity "high".
5. WHEN vulnerable dependencies exist, THE `get_top_risk_drivers()` function SHALL include a signal identifying the count of vulnerable dependencies, with category "vulnerability" and severity "high".
6. THE `get_top_risk_drivers()` function SHALL accept `per_repo_results` and `merged_graph` as parameters to generate signals from both repo-level and dependency-level data.
7. WHEN the aggregate risk level is "LOW", THE `get_top_risk_drivers()` function SHALL return at least 1 positive signal (e.g., "All components show strong maintenance activity") so that the output feels intentional rather than empty.

### Requirement 5: Improved Risky Dependencies Handling

**User Story:** As a user, I want dependencies to be evaluated and displayed even when they do not map to a GitHub repository, so that I see a complete picture of my dependency risk surface.

#### Acceptance Criteria

1. WHEN `compute_top_risky_dependencies()` returns an empty list, THE Overview_Page SHALL display a contextual message indicating that no risky dependencies were identified, rather than a generic empty state.
2. WHEN unmapped dependencies exist in the merged graph, THE `compute_top_risky_dependencies()` function SHALL include the unmapped dependencies in its output with default risk values (`risk_score` of 0, `risk_label` of "LOW", `cve_count` of 0).
3. WHEN the Risky Dependencies section contains only low-risk or unmapped dependencies, THE Overview_Page SHALL display a message indicating that all analyzed dependencies show low risk.

### Requirement 6: Insight Statements Engine

**User Story:** As a user, I want the system to generate human-readable insight statements that interpret what my system's risk posture means overall, so that I can quickly understand the key takeaways distinct from the factual risk driver signals.

#### Acceptance Criteria

1. THE `compute_insight_statements()` function SHALL accept `system_risk_summary`, `per_repo_results`, and `merged_graph` as parameters.
2. THE `compute_insight_statements()` function SHALL return a list of Insight_Statement strings, each providing an interpretive conclusion about the overall system risk posture. Insight Statements describe "what this means overall" (e.g., "Your system appears stable and well-maintained") and are distinct from Risk Drivers which describe "what is affecting risk" (e.g., "No vulnerable dependencies detected").
3. WHEN no vulnerable dependencies exist, THE `compute_insight_statements()` function SHALL include an interpretive statement such as "Your dependency supply chain appears clean and well-maintained".
4. WHEN all repos show low maintenance risk, THE `compute_insight_statements()` function SHALL include an interpretive statement such as "Your repositories demonstrate consistent maintenance practices".
5. WHEN high-risk repos exist, THE `compute_insight_statements()` function SHALL include a statement identifying the count and names of high-risk repositories and what this implies for the system.
6. WHEN dependencies are used by multiple repos, THE `compute_insight_statements()` function SHALL include a statement about dependency concentration and its implications.
7. THE `compute_insight_statements()` function SHALL return between 1 and 6 statements.

### Requirement 7: Frontend Rendering Updates

**User Story:** As a user, I want the Overview page to render the new explanation text, signal-based drivers, improved empty states, and correct dependency counts, so that the UI reflects the upgraded interpretation layer.

#### Acceptance Criteria

1. WHEN scope data is loaded, THE `renderRiskSummary()` function SHALL display the `risk_explanation` text below the system summary sentence.
2. WHEN scope data is loaded, THE `renderRiskSummary()` function SHALL display the `key_factors` list as visual tags or chips below the risk explanation.
3. WHEN scope data is loaded, THE `renderRiskSummary()` function SHALL display the `recommended_action` text as a call-to-action below the key factors.
4. WHEN scope data is loaded, THE `renderKPIs()` function SHALL display the `total_unique_dependencies` value from the System_Risk_Summary, which includes all user-provided dependencies.
5. WHEN scope data is loaded, THE `renderPriorityRisks()` function SHALL display contextual empty state messages based on the aggregate risk level when no priority risks exist.
6. WHEN scope data is loaded, THE `renderRiskDrivers()` function SHALL render Risk_Driver_Signal objects as signal cards showing the factual risk signal, category badge, and severity indicator.
7. WHEN scope data is loaded, THE `renderRiskyDeps()` function SHALL display contextual empty state messages when no risky dependencies exist.
8. THE Overview_Page SHALL render insight statements from `compute_insight_statements()` in a dedicated section or integrated into the risk summary area, visually distinct from the risk driver signals.

### Requirement 8: Preservation of Existing Behavior

**User Story:** As a developer, I want the upgrade to preserve all existing scoring formulas, graph structure logic, API contracts, persistence behavior, and page layout, so that the upgrade is purely additive.

#### Acceptance Criteria

1. THE upgrade SHALL NOT modify the `_risk_label_from_score()` function or its thresholds (LOW < 0.30, MEDIUM 0.30–0.59, HIGH >= 0.60).
2. THE upgrade SHALL NOT modify the `merge_graphs()` function or its node/edge deduplication logic.
3. THE upgrade SHALL NOT add new API endpoints; all changes SHALL be additions to existing response payloads from `compute_system_risk_summary()`, `compute_priority_risks()`, `compute_top_risky_dependencies()`, and `get_top_risk_drivers()`.
4. THE upgrade SHALL NOT modify the SCOPE_STORE persistence mechanism or add database persistence.
5. THE upgrade SHALL NOT modify the overall page layout structure of `ui/overview.html`; changes SHALL be limited to content rendering within existing sections.
6. THE upgrade SHALL NOT modify the `priority_score` formula: `SEVERITY_BASE[severity] + (usage_count * 0.5) + (cve_count * 1.0)`.
